# LingoLife 3D 主流程架构

版本：0.8
状态：现有 3D 基线与 2026-09-03 产品纵切的首个可运行切片已实现；完整 Agent 默认合同、布局版本历史和高级空间校验仍待硬化
范围：Web 端唯一玩家主流程；暂不实现宠物

## 1. 产品目标

LingoLife 的玩家端不再区分 2D 与 3D 路由。登录后先完成必要的首次介绍和居民建组，再进入一座可观察、可聚焦、会随日期和居民状态变化的 3D 天空之城。已有合格阵容的返回用户直接同步世界；schema v3 前已经存在的单 Emma 账号是为避免锁死旧用户而保留的明确兼容例外，可继续进入并应提示补足第二名居民，不能扩展到新账号。

玩家始终保持外部身份：

- **观察者**：浏览整座天空之城、居民位置、地点、关系与当天事件。
- **管理者**：选择居民或地点，进行英语对话、查看信息、配置角色与执行有限的管理操作。

玩家不会附身或直接控制 NPC。NPC 的人格、情绪、关系、计划、记忆与目标由服务端世界状态决定。

## 2. 唯一主流程

```text
登录
  ↓
读取账号的 onboarding 状态
  ├─ 未完成 → 世界介绍 → 选择并创建 2～8 名居民 → 编辑完整默认值 → 确认共享住宅阵容
  └─ 已完成 → 继续
  ↓
同步服务端世界快照与布局版本
  ↓
3D 天空之城观察视角
  ├─ 选择居民 → 进入跟随镜头 → 观察自主行程 → 查看事件或进入英语对话
  ├─ 选择建筑 → 聚焦地点 → 查看介绍/在场居民/事件 → 选择交互
  ├─ 打开角色管理 → 在 8 人上限内创建或编辑居民公开设定 → 服务端校验并保存
  └─ 打开学习进度/设置 → DOM 覆盖层 → 返回原视角
```

不新增 `/3d`，也不提供长期并行维护的 2D 玩家入口。管理后台保持独立域名和 DOM 界面。

## 3. 客户端分层

### 3.1 React 应用层

负责身份、路由状态、服务端请求、流式对话、设置、学习进度、角色编辑与错误恢复。React 是唯一业务状态入口，Three 场景不直接调用后端。

### 3.2 React Three Fiber 场景层

负责悬浮城市平台、道路、建筑、植被、居民、镜头、灯光、云层和选中反馈。场景只消费经过归一化的世界快照并发出语义事件：`selectNpc`、`selectLocation`、`returnOverview`。

### 3.3 DOM 交互层

负责字幕、漫画气泡、历史记录、输入框、学习反馈、设置和无障碍替代信息。所有重要文字必须可选择、可由屏幕阅读器读取，并可在 WebGL 降级时继续使用。

### 3.4 服务端权威层

服务端决定日期、时间段、居民位置、活动、事件、关系、记忆和学习结算。客户端动画可以预测和插值，但不得自行创建会影响游戏结果的事实。

## 4. 世界与时间

- 服务端城市坐标表达地点所属区域和相对位置；渲染层先做比例变换，再由确定性的地块解析器吸附到最近合法地块。地点、住宅、居民锚点和镜头焦点必须共用同一份解析结果。
- 世界读取调用一次事务化 `advance_world(now)`，把到期 Life Action、资源、碰撞、故事与关系推进至服务端当前时间；事件不再按游戏日强制派发。
- 服务端在快照中返回 `world_version`、`server_time` 和 `next_transition_at`；客户端只建立一个到期刷新调度器，并用版本阻止旧响应覆盖新状态。
- 每名居民拥有具体 `current_action`。位置由动作、路线、资源锚点和时间决定，不再用 morning / afternoon / evening 静态槽位冒充实时生活。
- 全城 NPC 不再强制保持大距离；只在表现层使用小幅站位避让。相遇、排队和共享资源必须允许 NPC 合理靠近。
- 建筑提供地点类型、简介、视觉主题、当前居民与活动摘要。
- NPC 与 NPC 之间使用有方向的关系边：A 对 B 的信任不必等于 B 对 A。
- 当前天空之城的逻辑范围为 `56 × 38` 世界单位。主体是有厚度和悬浮结构的城市平台，由六个不对称主题街区、口袋公园和城市广场组成，不再使用海岸或孤岛轮廓。
- 东、西主干云路和北部天穹路共三条道路从平台边缘继续伸向云层，表达当前城市只是更大世界中的一个节点；道路末端不可做成封死的地图边界。
- 平台下方与外围使用成组的离散云层营造云海感，云团包裹城市轮廓，同时让蓝天透出并为建筑主体保留清晰净空区。不得使用覆盖整个 Canvas 的白色半透明雾层或不透明浅色云海平面，以免重现白雾遮挡、洗白和屏闪问题。
- 天穹、环境反射、主辅光、软阴影、环境光遮蔽和抗锯齿由统一渲染管线管理。地图场景不得再各自创建相互冲突的背景、海面或全局灯光。
- 当前版本不实现雨、雪、雷暴等天气变化。时间段仍可影响整体光色，但视觉质量、角色可读性和移动端稳定性优先于天气多样性。
- 道路、建筑和街道设施使用 KayKit City Builder Bits 的实例化模型；业务地点按固定规则收束到资产族：住宅使用 `building_A/B/C`，商业与咖啡馆使用 `building_D/E`，办公及公共设施使用 `building_F/G/H`。
- 道路与建筑地块共用 `2.6` 单位模数。合法地块必须完整位于平台轮廓内、不得占用道路格、至少一侧临路；业务地点、唯一共享住宅和普通城市肌理按稳定 ID 独占地块，建筑缩放硬限制在其声明占地内。
- 城市肌理以 54 栋为构图目标，按六个街区和 `4 × 3` 空间网格的最低密度优先补齐，不允许再用全局随机截断产生局部空洞。不可建造的街区内部使用校园公园、喷泉广场和车站停车区形成有目的的开放空间。
- 居民必须站在其解析后建筑临路一侧的人行区域，不再使用原始业务坐标随机偏移。地图角色按素材族归一到约 `0.54–0.75` 世界单位高，并以独立透明点击体维持移动端命中范围。

### 4.1 NPC 行程、生活动作与跟随镜头

- 世界快照中的 Life Action 可以处于 `planned / traveling / performing / blocked / retrying / completed / abandoned / interrupted`。客户端以服务端给出的开始、到达和结束时间在路网上插值，只负责表现，不回写世界事实。
- 步行路线由道路模块派生的人行道图和确定性 A* 生成；不可达时角色停在起点等待刷新，禁止用穿过建筑的直线兜底。
- 到达后角色前往地点或室内资源锚点。普通 Ambient 不显示任务标志；Moment 只做克制提示；Incident 可以在干预窗口内显示服务端允许披露的 Trouble Signal。同场参与者使用稳定交互站位，避免模型和姓名重叠。
- `observe` 只记录观看并返回当前表演，不触发结算；玩家不处理时世界按权威时间自主完成，`intervene` 才提交管理动作。
- 动作导演根据 `server_time - started_at` 恢复 enter / loop / react / exit 的正确阶段，刷新、切后台或换设备不得从第一拍重播。
- 居民列表始终可见。选择居民只切换连续阻尼的跟随镜头，不会自动打开聊天或夺取角色控制权；玩家可随时返回总览，NPC 行程继续按服务端时间推进。
- 跟随状态下暂时锁定旋转、平移与缩放，由系统维持可读的近景构图；总览状态恢复城市浏览操作。

### 4.2 Residence 与 Household 剖面场景

- Residence 是地图上的空间实体，Household 是共同居住成员与共享状态。当前每个玩家世界只有一个活跃 Household 和一个共享 Residence，所有 2～8 名活跃居民都把该地点作为回家、睡眠和 Household 行为的权威住宅；不得继续在地图上为每名居民点亮独立住宅。
- 住宅剖面至少提供客厅、厨房、浴室与卧室，以及电视、料理台、浴室和床等资源锚点。
- 占用、等待、库存、脏盘子和噪声等事实由服务端决定，Three 场景只展示。点击资源可以查看可观察状态，不显示隐藏 Desire 或关系数值。
- 城市主场景保持一个持久 Experience Canvas。首轮生活现场在覆盖层开启轻量角色 Canvas 时会暂停城市 Canvas，并在关闭后恢复和主动失效重绘，保证同一时刻只有一个 3D 场景持续渲染；后续若把住宅剖面并入主场景，再统一为单 Canvas 路由。
- 当前阶段只制作和发布一套达到正式品质的共享住宅室内，不再以 11 套低完成度主题分散灯光、构图、锚点、动画接触和移动端优化。该套场景内部可以包含客厅、厨房、浴室、卧室及必要的过渡空间；城市公共地点本轮继续使用外观聚焦、地点资料和受约束的事件舞台，不承诺各自拥有完整可进入室内。
- 共享住宅使用现有已授权资产并保存为版本化布局清单。房间、门、路径、交互资源和角色站位使用稳定语义 ID；替换美术模型不能改变服务端事实 ID，故事文本也不能凭空改变位置事实。
- 家具模型各自拥有局部 `Suspense` 与错误边界；加载慢或单个 `.gltf`/纹理损坏时显示同尺度几何占位，房间外壳、关闭按钮和其余模型仍保持可用。住宅相机必须明确朝向房间中心，并由守卫覆盖窄屏视锥，禁止退回 Three 默认的 `-Z` 朝向。
- `sleep`、`shower` 等私密行动由服务端公开投影统一收束成“在家处理私人事务，暂时不便打扰”。地图不显示精确房间或物品，住宅切面只显示房间正在进行私人活动，不渲染居民模型；客户端不得从隐藏需要值重新猜测具体行为。

### 4.3 品牌加载与城市入场

- 首次账号在加载 3D 城市前显示可回顾的产品介绍：说明玩家是观察者/有限管理者、NPC 会自主生活、建议不保证被接受、英语用于理解和影响而非遥控。介绍完成后进入 Household 建组，不以空城或默认单角色代替引导。
- 建组界面维护 2～8 人阵容，并从不重复的版本化原型生成默认角色卡。每张卡提供 3D 预览以及姓名、年龄、与玩家的初始关系描述、职业、人格标签、兴趣、长期目标、模型和恋爱自主权等首轮核心编辑入口；确认前可以增删、逐人重抽或整组重抽，少于 2 名、超过 8 名或校验失败时不能提交。喜恶、怪癖、习惯、家务倾向、Household 角色和阵容差异评分仍需在后续合同扩展中补齐。
- 世界创建必须使用单个原子请求或等价事务：创建/更新全部居民、客观结构关系、唯一 Household、唯一 Residence 成员关系和初始世界种子。中途失败不能留下“部分角色已进入城市”的半初始化世界。
- 登录校验、应用分包和 3D 场景准备共用同一套 DOM/CSS 云层加载壳，避免白屏及多个加载画面跳变。创建完成后由建组界面自然过渡到云层加载，再揭示城市；返回用户跳过建组但不跳过必要资源加载。
- 地图左上角不常驻 Logo。Logo 只在云层加载画面中出现，场景至少完成三帧有效渲染后才触发揭幕。
- 首次入场按会话轮换云门向两侧散开、云路下沉、城市从云上升起三种动画；同一会话返回地图使用较短淡入。
- 12 秒仍未得到有效场景帧时显示重试和列表降级入口；`prefers-reduced-motion` 下取消云层位移和镜头飞行，仅保留短淡入。

### 4.4 地图作者工具与镜头所有权

- 城市与共享住宅作者工具进入已鉴权的管理端，按需加载 3D 编辑代码。只有开发/运营角色可以创建草稿、预览、校验、发布和回滚；普通玩家域名、玩家 API 和普通管理员只读页面均不能获得布局写权限。
- 编辑器只展示项目资产清单中已授权、已转换和通过运行时守卫的模型。城市模式支持道路、建筑、公共地点、树木和街道小品；住宅模式支持房间边界、门、家具、装饰、资源锚点、站位和路径节点。不得提交任意外部 URL、脚本或用户上传模型。
- 草稿与已发布布局均有版本号、作者、时间、变更说明和父版本。预览不影响玩家；发布后新世界快照引用新版本，回滚切换到已验证版本而不是直接修改数据库中的 NPC 事实。玩家端旧 `?mapEditor=1` 已移除，正式编辑只从管理端进入。具体约束见 [MAP_AUTHORING.md](MAP_AUTHORING.md)。
- 放置、移动、旋转、导入和发布共用服务端/构建期可复现的空间校验。城市必须检查道路双向连通、平台边界、建筑占地和行程区域；住宅必须检查房间可达、门连通、碰撞、资源容量、交互朝向和每个 Life Action 所需锚点，禁止出现预览合法但发布后压路、穿模或行为无处执行。
- 作者工具只能定义模拟可用条件。它不能指定 NPC 当下位置、强制传送、修改 Need/Emotion/Desire/Commitment/关系/记忆、清除 Thread、结算事件或重抽种子。布局版本变化由服务端在事务中完成资源租约迁移、动作完成/中断/重规划，失败则拒绝发布。
- 总览或俯瞰状态下，一旦玩家开始拖拽或缩放，手动控制立即取得镜头所有权；尺寸更新和旧聚焦动画不得再次覆盖玩家镜头。
- 跟随状态使用稳定的地块朝向计算镜头偏移，并按实际帧间隔阻尼追随。禁止逐帧寻找最近道路来决定镜头方向，以免居民跨格时发生左右跳变。

当前已落地的是首版 authoring slice：现有管理员会话可在同一页面编辑城市道路、建筑、街道设施、装饰，以及共享住宅四个固定房间的资产 placement；前端提供 2D 拖拽、数值变换、3D 预览和 JSON 导入导出，后端用白名单 schema 校验后覆盖单个 published 布局，reset 只恢复代码内置默认布局。首版还会拒绝缺失 shared-home/业务地点、城市越界、道路与建筑中心点重合以及空基础房间。共享住宅的代码默认值已有单一版本化布局合同，构建时检查 2/4/8 人边界、8 个私人床位、厨房/电视/浴室容量、资产占地与 13 类 Life Action 锚点；渲染层会把跟随家具移动的站位换算到已发布 placement。它还不是上述目标中的独立作者角色、服务端草稿、不可变发布历史或真正版本回滚，也尚未实现道路接口连通、任意作者草稿的完整占地/可达性/锚点校验和运行中租约迁移校验。产品发布口径与验收不得把默认合同校验说成任意草稿校验，也不得把 reset 写成版本回滚。

## 5. 角色与对话

角色外观由同一份 `AvatarConfig` 驱动角色编辑器、城市模型和对话模型，避免预览与实际上身不一致。`AvatarConfig.model` 是稳定的资产清单 ID，而不是客户端可提交的任意 URL。

首次建组的默认生成器最终应输出完整 Persona、Avatar 和 Household 行为合同。当前首版从 12 个不重复原型中生成 NpcProfile 的核心公开字段，服务端再由人格标签编译六个人格轴和行为倾向，并为所有同住者建立 housemate 结构关系；成对心理边可以从中性基线开始，由之后的真实共同经历拉开。当前实现尚未持久化或开放喜恶、怪癖、习惯、家务倾向、Household 角色和共同历史 Hook，也没有完整阵容差异评分。目标仍是对整组居民检查人格距离、兴趣重叠、日程、家务倾向、社交方式和边界，避免 2～8 张只换名字和衣服的克隆卡；不得为了“有戏”直接写入恋爱、世仇或已结算 Incident。确认后刷新不再重抽已成为世界事实的合同。

当前提供两个不能混用骨骼动画的资产族：

- **Chibi 组合角色**：一个共享骨骼模型，允许从资产真实存在的 6 种发型、5 组服装和 5 种配饰中组合，并允许有限的肤色、发色和服装色调整。
- **RG Poly 城市居民**：16 个完整预设，身体和衣装是同一个蒙皮网格，因此编辑器只开放完整造型和发色，不伪造素材中并不存在的五官、衣裤拆分选项。

人物公开表现由同一份 `CharacterExpressionPlan` 驱动地图、跟随视角、住宅切面、生活事件、旧社交事件和聊天舞台。它把服务端公开的行为类型、阶段、粗粒度情绪/精力、麻烦信号、故事结果和公开关系频道映射为兼容动画、Kenney 状态气泡及轻量 VFX；兴趣行为还根据音乐、绘画、摄影、健身、烹饪、阅读等具体主题分别表现，不再统一显示音乐或“投入兴趣”。麻烦信号优先于普通赶路状态，负面结局不得统一播放开心表情。

当前 Chibi 与 RG Poly 模型没有面部 Morph，且已下载的 KayKit / Quaternius 生活动作与它们的骨骼不兼容。因此本阶段的“表情”由真实兼容的身体动画、授权状态气泡和 VFX 共同表达；坐椅、躺床、进食、手持物等精确接触动作必须先做离线重定向与 IK 校正，不能在运行时硬套骨骼造成穿模。

旧账号中的程序化外观值会在客户端映射到最接近的新部件；模型加载或 WebGL 资源失败时才回退到旧程序化角色，避免单个素材损坏造成白屏。

事件系统只向客户端发送语义动作 `idle / talk / listen / happy / sad / tired / look_around / walk / run / jump / crouch / push`。服务端结合当前事件阶段、结局和情绪校验 AI 候选动作；两个资产族再分别把同一语义动作映射到自己的真实动画片段。AI 不能返回任意动画名，也不能借动作改变事件结果。

个人事件的阶段和结局使用版本化的 `performance v1` 表演契约。契约由有限的
`beats`、结束后的 `hold_cue` 以及每拍的语义 cue、角色、时长、循环、转场、朝向和能量组成；
它不包含 GLB clip 名。服务端负责校验和选择剧情动作，客户端导演负责片段变体、交叉淡化、播放速率、
自然待机和资产族差异。旧内容只有一个 `animation_cue` 时会自动合成兼容表演。

客户端按情境覆盖表演优先级：权威行程状态始终保持走/跑；玩家发言时 NPC 倾听；NPC 流式回复时说话；
回复完成后播放当前阶段或结局反应；地图待办居民播放不含自言自语的环境序列。减少动态效果模式只保留安全的
静态/低能量 hold。NPC 社交事件观看界面必须使用双方真实外观并让角色相向，不能退回姓名首字母代替表演。

对话采用聚焦舞台：

- 镜头从天空之城总览平滑飞向居民所在地点。
- 前景保留玩家观察者存在感，但不生成玩家化身身份。
- NPC 与玩家消息以 DOM 漫画气泡呈现；DeepSeek 文本按流式增量淡入。
- 最新气泡保留到下一条消息出现，再进入历史层。
- 历史、风景介绍和实时对话是互斥状态，不遮挡 NPC 主体。
- 对话结束后返回此前的城市镜头位置，而不是重建整个场景。

## 6. AI 与规则边界

实时对话同时执行两条支线：

1. 对话模型根据角色契约、当前状态、关系、目标、事件、记忆和学习难度生成英文回复。
2. 保守分析器提取英语证据、有限语义信号和候选记忆。

模型不能直接决定数值、掌握度、事件结果或 NPC 位置。服务端规则层验证模型输出后再结算；翻译是独立步骤，不改变英文原文。

NPC 自主事件由规则候选集、人物设定、日程、地点和方向性关系筛选。模型只负责把已确定的事实组织成自然语言，不负责凭空决定世界事实。

## 7. 性能预算

移动端仍是硬约束，但当前阶段按用户要求先保留原始素材质量。资源按场景和角色按需加载，不把整个角色库塞进首屏：

| 项目 | 首屏目标 | 上限 |
| --- | ---: | ---: |
| 初始 JS（gzip） | 500 KB | 850 KB |
| 世界模型资源 | 1.1 MB | 2 MB |
| 首个 Chibi 角色 | 14.3 MB | 16 MB |
| 首个城市角色及动画库 | 2.4 MB | 3 MB |
| Draw calls | 80 | 140 |
| 可见三角形 | 180k | 350k |
| 动态灯光阴影 | 1 个 | 2 个 |
| DPR | 1.0–1.5 | 2.0 |
| 目标帧率 | 45 FPS | 30 FPS 降级线 |

实现约束：

- 重复建筑、树木和路灯使用实例化。
- 远景采用简单几何或 LOD；不可见分区暂停动画。
- 阴影只覆盖聚焦区域；观察视角优先烘焙感光照。
- 页面隐藏、低电量或检测到持续掉帧时降低 DPR、阴影和环境特效。
- `prefers-reduced-motion` 下取消镜头飞行和弹簧位移，仅保留短淡入。
- Three 依赖按玩家端加载；管理后台只有布局编辑路由按需加载 3D 代码，其余管理页面不加载。
- 16 个城市居民预设不会主动全部预加载；只请求世界中实际出现或编辑器当前预览的模型。
- 后续发布优化优先使用 meshopt/纹理压缩和 HTTP 长缓存，不以删除动作、角色选项或城市内容来换体积。

## 8. 可靠性与降级

- WebGL 初始化失败时显示可操作的居民和地点列表，而不是空白页。
- 资源加载使用局部占位体；单个模型失败不阻塞世界。
- 断线时保留最后一次世界快照和未发送输入；重试复用幂等键。
- 服务器返回的新世界版本才覆盖客户端缓存。
- 对话、创建角色和事件结算仍由 API 测试覆盖，不依赖视觉测试才能验证业务正确性。

## 9. 验证门槛

发布前必须通过：

- 新账号的介绍、2～8 人随机建组、逐人编辑、整组校验、原子确认和再次登录流程；
- 0、1、2、4、8、9 人边界测试：0/1 人不能进入世界，2～8 人可运行，9 人被拒绝且不产生半存档；
- 所有活跃角色的回家目的地、私人房间和 Household 资源均解析到同一个 Residence；
- 单套共享住宅在桌面和移动端的构图、房间切换、路径、资源占用、隐私遮挡、动作锚点和加载降级走查；
- 管理端城市/住宅草稿、资产白名单、空间校验、发布、回滚、权限隔离以及“布局不能写 NPC 动态事实”测试；
- 旧账号迁移保留角色、外观、关系、消息、记忆、事件、目标和学习记录，且超限账号不被静默截断；
- 后端完整 pytest。
- 前端 ESLint、TypeScript、生产构建。
- 3D 世界的坐标、选择、镜头与 WebGL 降级单元测试。
- 角色配置到 3D 部件映射测试。
- 桌面鼠标、键盘、移动端单指/双指和减少动态效果的人工走查。
- Docker 镜像构建、健康检查、线上登录、城市、对话流、后台回归。

## 10. 本轮交付边界

本轮纳入：首次产品介绍、2～8 人完整随机建组与编辑、单一共享 Household/Residence、单套正式品质住宅室内、管理端现有资产城市/住宅作者工具、版本化发布与回滚，以及既有 3D 天空之城、角色、动画、对话、方向性关系、自主事件和学习/记忆接口的兼容集成。
